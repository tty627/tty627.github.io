近期的一段实习工作主要围绕大模型 Agent 评测：我在使用 [AgentCompass](https://github.com/open-compass/AgentCompass) 运行与分析 [Terminal-Bench 2.1](https://github.com/harbor-framework/terminal-bench-2-1) 相关任务，也会检查和调整任务约束。真正开始处理这些工作后，我发现 Agent 评测里最难回答的问题，往往不是「模型有没有给出答案」，而是：

> 我们凭什么确认，它真的把任务完成了？

本文只讨论公开工具和通用方法，不涉及任何内部数据、未公开任务或受限结果。

## 「执行结束」不等于「任务完成」

终端类 Agent 很容易给人一种已经完成工作的错觉。

它运行了许多命令，生成了文件，最后也返回了一段看起来合理的总结。但这些现象最多只能说明一次执行已经结束，不能直接证明目标状态已经出现。

我现在更愿意把一次评测拆成三个层次：

1. **执行结束**：Agent 停止运行并提交结果；
2. **表面完成**：输出内容看起来符合任务描述；
3. **可验证完成**：存在独立、明确且可复现的证据证明任务成功。

只有第三层适合作为可靠的评测结果。

例如，一个任务要求 Agent 修复程序。Agent 声称已经修好，甚至附上了修改说明，但真正重要的证据可能是：

- 修改后的程序能否在指定环境中运行；
- 原有测试是否仍然通过；
- 目标失败用例是否被修复；
- 是否只修改了允许修改的文件；
- 结果能否在干净环境中复现。

自然语言总结可以帮助人理解过程，却不应该成为判定成功的唯一依据。

## 约束不是越多越好

修改和设计任务约束时，一个很自然的做法是继续增加规则：不能改某个目录、必须使用某种工具、输出必须包含某些字段……

但约束越多，并不一定意味着评测越可靠。多余的限制可能把原本考察解决问题能力的任务，变成对提示词细节的记忆测试。

我会用四个问题检查一条约束是否值得保留：

- **必要吗？** 去掉它会不会让任务目标发生变化？
- **可验证吗？** 能不能通过程序或明确证据判断它是否满足？
- **一致吗？** 它是否与环境条件、其他约束或验证逻辑冲突？
- **相关吗？** 它限制的是任务目标，还是某一种不必要的实现方式？

理想的约束应描述成功状态和真实边界，同时给 Agent 留出合理的实现空间。与其规定 Agent 必须依次执行哪些命令，不如明确最终产物、不可破坏的状态，以及验证程序会检查的条件。前者容易把评测变成流程复刻，后者更接近真实的软件工程任务。

## Verifier 也需要被验证

在自动评测中，Verifier 常被当作最终裁判。但它本身同样可能存在问题。

一个过于宽松的 Verifier 可能接受错误结果；一个过于严格的 Verifier 则可能拒绝正确但实现方式不同的答案。还有一些情况下，任务描述与验证逻辑对「成功」的定义并不完全一致。

因此，检查任务时不能只问「Agent 为什么失败」，还需要反过来问：

- Verifier 检查的状态是否真的代表任务目标？
- 是否存在绕过验证但没有真正完成任务的方式？
- 正确结果是否可能因为路径、格式或实现差异被误判？
- 验证过程是否依赖执行后残留的临时状态？
- 同一结果在干净环境中能否得到一致判定？

评测对象并不只有 Agent。任务描述、运行环境和 Verifier 共同组成了一个评测系统，任何一部分不稳定，最终分数都可能失去解释力。

## 先分类失败，再讨论能力

一次任务失败可能有很多来源。如果把它们全部记作「模型能力不足」，结论通常会过于草率。

在实践中，我倾向于把失败至少分成四类：

### 1. Agent 行为失败

Agent 对目标理解错误、选择了不合适的工具、遗漏关键步骤，或在已有证据不足时过早宣布完成。

### 2. 环境与工具失败

依赖缺失、网络或权限受限、命令行为与预期不一致，或者初始状态不完整。这类失败未必反映 Agent 对任务本身的理解。

### 3. 任务定义失败

描述存在歧义，约束互相冲突，或成功标准没有被完整表达。此时不同 Agent 可能做出各自合理但互不兼容的解释。

### 4. 验证失败

Verifier 存在误报、漏报或对实现细节过度敏感，导致实际状态与最终判定不一致。

失败分类的意义，不是为 Agent 找借口，而是避免用错误的原因解释评测结果。只有知道失败发生在哪一层，后续的任务修订和模型分析才有意义。

## 可复现性需要留下足够证据

Agent 任务通常包含许多状态变化。只保存最后一段回复，很难还原问题发生的过程。

一次更容易复现的评测记录，至少应尽量包含：

- 初始环境及关键依赖版本；
- 任务输入与约束版本；
- Agent 的命令或工具调用记录；
- 执行产生的文件和状态变化；
- Verifier 版本及完整输出；
- 超时、重试和资源限制策略。

这些记录让评测从一个孤立的分数，变成可以检查的实验过程。尤其是在任务或约束发生修改时，版本信息很重要。否则，即使两个结果使用了相同的任务名称，也可能实际上对应不同的环境和判定标准。

## 我现在如何理解一次可靠的 Agent 评测

经过这段实践，我形成了一个还在迭代中的判断：

> 好的 Agent 评测，不只是给模型设置一道难题，而是建立一条从任务目标到验证证据的完整链路。

这条链路需要做到：

1. 任务描述清楚表达目标与边界；
2. 环境能够稳定支持任务执行；
3. 约束必要、可检查且彼此一致；
4. Verifier 检查真实的目标状态；
5. 执行过程留下足以复现的证据；
6. 失败能够被分类，而不是被简单归因。

Agent 的能力当然重要，但评测系统本身是否可信同样重要。一个任务越接近真实世界，成功状态通常也越复杂；而越复杂的成功状态，就越需要严谨的验证设计。

我还没有找到适用于所有任务的统一答案。不过，开始区分「看起来完成」与「能够被证明完成」，已经改变了我设计和阅读 Agent 评测结果的方式。
